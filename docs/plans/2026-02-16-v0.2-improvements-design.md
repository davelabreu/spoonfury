# Spoonfury v0.2 Improvements — Design Doc

**Date:** 2026-02-16
**Status:** Approved
**Author:** Claude + davel

## Overview

Six targeted improvements to the v0.1 prototype, identified by code review and live browser testing. Focus areas: data quality, the core fork-to-book loop, recipe editing, and resilience.

## Problem Statements

1. **Blank ingredient bug** — `CreateRecipePage` submits empty ingredient rows. They render as empty checkboxes on the recipe page and inflate the Instacart item count.
2. **Fork loop is incomplete** — Forking creates a recipe but doesn't save it to a book, breaking the intended `fork → book → edit` flow.
3. **No recipe editing** — There is no way to edit a recipe after it's created or forked.
4. **Weak CTAs** — "Make it mine" is buried at the bottom of the recipe page. The page has no edit affordance for recipe owners.
5. **No "Add to book" for owned recipes** — Users can't add their own (non-forked) recipes to a book from the recipe page.
6. **No error states** — Failed API fetches leave pages stuck on "Loading..." forever.

## Design Decisions

### 1. Blank Ingredient Fix

**Frontend only.**

- `CreateRecipePage`: filter out rows where `name.trim() === ""` before POSTing to the API.
- `IngredientChecklist`: filter blank ingredients before rendering so stale bad data doesn't display.

### 2. Revised Fork Flow — Fork = Copy + Save to Book

The fork modal is simplified. Ingredient editing is **removed** from the fork step entirely.

**New fork modal UX:**
- Shows the recipe title being forked
- Dropdown: "Save to which book?" (populated from `GET /api/books/`)
- If no books exist: inline message "You don't have a book yet — [Create one]" linking to `/books`
- Single button: "Fork it"
- On success: navigate to `/books/:id` (the chosen book), not the new recipe

**Backend change:**
- Fork endpoint currently validates ≤3 ingredient changes and requires modified ingredients in the request body. With fork-as-copy, the frontend sends the parent's ingredients unchanged. The backend validation still runs (0 changes always passes), but no ingredient editing happens at fork time.
- The ≤3 change constraint is preserved in the codebase for future use but is no longer triggered by this flow.

**Navigation:**
- After fork → `/books/:id` so the user immediately sees their forked recipe in context.

### 3. Recipe Edit Page (`/recipes/:slug/edit`)

**New page.** Accessible only to the recipe owner.

- Full editing: title, description, serves, ingredients, instructions, notes.
- Category is **locked** (inherited from the original; cannot be changed).
- Reached via an "Edit" button on the recipe page (shown only to the owner).
- On save: `PATCH /api/recipes/:slug/` → redirect back to `/recipes/:slug`.

**Backend change:**
- Add ownership check to `PATCH` and `DELETE` on `RecipeViewSet`. Return `403` if `request.user != recipe.author`.

### 4. CTA Layout on Recipe Page

The action buttons move to the **recipe header area** (below title/author line), visible without scrolling.

- **Viewing someone else's recipe (logged in):** "Make it mine 🍴" button in header
- **Viewing your own recipe (logged in):** "Edit" button + "Add to book" inline select in header
- **Logged out:** no action buttons (read-only)
- Remove the buried bottom-of-page button entirely.

### 5. "Add to Book" for Owned Recipes

For the recipe owner, an inline book select appears in the header area:

- Renders a `<select>` populated from their books
- On change: immediately calls `POST /api/books/:id/add-recipe/` with the current slug
- Shows a brief "Saved!" confirmation, then resets
- If no books: "Add to a book — [Create one]" link

The backend `add-recipe` endpoint already exists; this is frontend-only.

### 6. Error States on API Fetches

All pages that fetch data add a `.catch()` handler:

```ts
api.get(...).then(setData).catch(() => setError("Failed to load. Try refreshing."))
```

Pages affected: `RecipePage`, `HomePage`, `BooksPage`, `BookDetailPage`.
Render pattern: replace "Loading..." with `<p className="text-destructive">{error}</p>` when error is set.

## Out of Scope (v0.3)

- Remove recipes from a book (already exists in API, not yet in UI)
- Fork count display / social discovery
- User profile page
- ≤3 ingredient change constraint on the edit page (currently unenforced post-fork)
- `updated_at` in serializer
- Atomic fork count increment
- N+1 query in RecipeBookSerializer

## Notes for AI Agents

- The `add-recipe` backend endpoint is at `POST /api/books/:id/add-recipe/` with body `{ recipe_slug: string }`.
- The `share` endpoint uses `detail=False` and a custom URL pattern — do not confuse with the standard retrieve action.
- The `fork_recipe` view is in `views_fork.py`, not `views.py`.
- All frontend API calls go through `src/lib/api.ts` — do not use `fetch` directly.
- Shadcn components are in `src/components/ui/`. The `cn()` utility is in `src/lib/utils.ts`.
- TypeScript paths: `@/` resolves to `src/`. Configured in both `vite.config.ts` and `tsconfig.app.json`.
